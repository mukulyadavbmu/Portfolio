## Why this project matters

Financial software requires high reliability, complex state management, and an exceptional user experience. Eduvora demonstrates the ability to build a robust frontend architecture capable of handling heavy calculations (loan amortizations, eligibility scoring) entirely client-side without sacrificing performance. 

**Resume Mapping:**
- **Frontend/Systems:** React component architecture, Vite build optimization, client-side algorithms.
- **UX/UI Engineering:** Interactive dashboards, responsive design, data visualization.

---

## Problem & Motivation

Students often struggle to compare different loan options due to convoluted interfaces and hidden math. The goal of Eduvora was to bring transparency to education financing through a real-time simulation dashboard where students can adjust parameters (interest rates, tenure, principal) and instantly see the long-term impact on their financial future.

---

## Architecture

The application is a Single Page Application (SPA) built entirely on the client side to ensure immediate feedback for the calculators.

- **Build System:** Vite is used instead of Webpack for significantly faster Hot Module Replacement (HMR) and optimized production bundles.
- **Component Tree:** Highly modularized. Calculators, Path Comparisons, and the Simulation Dashboard are isolated components that receive state via a centralized context provider.

---

## Implementation Details

### Frontend Implementation
The core challenge was managing the state of multiple, interconnected financial variables. I implemented a robust state management pattern using React's Context API and `useReducer` for complex state transitions. This prevents prop-drilling and ensures that when a user updates their loan tenure, the amortization charts and eligibility components instantly re-render with accurate data.

### Security Implementation (Client-Side)
While financial data processing ideally occurs backend, this MVP handles estimations client-side. Strict input sanitization and boundary checking (e.g., preventing negative interest rates or abnormally large principals) were implemented to prevent calculation crashes (`NaN` propagation) and ensure data integrity within the app state.

---

## Scalability & Performance Optimizations

- **Bundle Size Optimization:** By utilizing Vite's native Rollup configurations, we ensure code-splitting is applied to the application routes. The heavy charting libraries are lazy-loaded only when the user navigates to the Simulation Dashboard.
- **Memoization:** Financial calculations running on every render can cause frame drops. `useMemo` was aggressively applied to the amortization algorithms so they only recalculate when the underlying loan parameters mutate.

---

## Testing Strategy

- **Validation Strategy:** Financial math must be exact. Unit tests were written for the core algorithmic functions (e.g., compound interest calculation, monthly EMI derivation) to ensure they match standard banking formulas perfectly, handling floating-point precision issues correctly.

---

## Tradeoffs, Failure Cases & Limitations

- **Client-Side vs. Server-Side Rendering (SSR):** I chose a pure client-side React approach (SPA) rather than Next.js SSR. 
- **Tradeoff:** While this slightly impacts initial SEO, it vastly improves the interactivity and speed of the financial calculators once the app is loaded. For a highly interactive dashboard behind a login wall, SPA is often the superior tradeoff.

---

## Measurable Results

- **Performance:** Achieved a perfect Lighthouse performance score (100) due to aggressive lazy loading and Vite's optimized build process.
- **Responsiveness:** The UI maintains a stable 60 FPS even when dragging slider inputs that trigger complex amortization array recalculations.

---

## Timeline, Lessons Learned, & Future Improvements

**What I'd do with more time:** 
Migrate the codebase to strict **TypeScript**. While JavaScript allowed for rapid prototyping of the MVP, the complexity of the financial data structures (loan objects, user profiles, amortization schedules) heavily warrants strict type checking to prevent runtime errors.
